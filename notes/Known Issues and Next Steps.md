## Testing conventions established this session (worth continuing)
- Always verify structural/scientific changes to `.smk` rules with a **real `snakemake -n` dry-run** (not just code review) — e.g. targeting a specific output file directly (`snakemake -n --configfile=... results/.../specific_output`) is faster than triggering the full `rule all` DAG when you just need to check one rule's behavior.
- After any backend route change, re-audit the **full route list** (`grep -oE '@app\.(get|post|websocket)\("[^"]+"\)'`) against what existed before — this is how the two dropped WS routes were caught.
- Test the packaged `.deb` **non-destructively** by `dpkg-deb -x` into a scratch folder and running the binary directly from there — no need for `sudo dpkg -i` to verify a build works.
- For dependency-graph fixes to a `pipeline.yaml`, don't just eyeball the JSON — **reimplement the client's `settle()` cascade in a throwaway Python script** against the real manifest and check what survives disabling a given tool. Caught the full extent of the SIGMA dependency gap this way (14 tools, not just the couple that were obviously wrong) before touching any code.
- Before trusting a tool's `requires`, `rule_names`, or other manifest wiring for a *new* pipeline, grep the actual `.smk` rule files for what each rule's `input:` really reads — the MAGMA graph in [[MAGMA Dependency Graph]] and the SIGMA gap in [[SIGMA Dependency Graph]] were both found this way, not by trusting what the manifest already claimed.
- When a real GUI screenshot tool isn't available, forcing a GTK/Flutter app through XWayland (`GDK_BACKEND=x11`) + `xwd` + a hand-written XWD→PNG parser is a viable fallback; `python-xlib`'s XTest extension can drive clicks the same way `xdotool` would. See [[Decisions Log]]'s pitch-deck export entry for the full recipe.
- **`starlette.testclient.TestClient.websocket_connect()` cannot test a background task surviving a client disconnect** — it spins up a fresh event loop (its own portal thread) per websocket connection, torn down when the `with` block exits, which kills any `asyncio.create_task()` scheduled during that connection along with it. To test a detached background task across connect/disconnect/reconnect cycles like production `uvicorn` actually behaves, run the real app via `uvicorn.Server(...).run()` in a background thread (one persistent event loop) and drive it with the real `websockets` client library instead. See [[Decisions Log]]'s "Database downloads" entry, 2026-07-16/17, for the full recipe — this cost real debugging time before being figured out.
- To verify a `.desktop`/launcher script actually works (not just "runs fine from my interactive shell"), test it with the *minimal* environment a real desktop launch provides, not your own shell's: `env -i` plus only `systemctl --user show-environment`'s real vars (PATH, DISPLAY, WAYLAND_DISPLAY, XAUTHORITY, DBUS_SESSION_BUS_ADDRESS). This is what caught the `flutter`-not-on-PATH bug in `run_dev.sh` — it worked perfectly in every interactive-shell test and would have shipped broken.
- **A second, distinct real-Snakemake-testing PATH gotcha (2026-08-07)**, beyond the already-documented `.venv` leak: manually prepending a *tool's own* conda env `bin/` (e.g. `.../envs/snakemake/bin`, to make the `snakemake` command reachable) onto `PATH` before `source activate <a different target env>` in the same shell leaves it stuck ahead of the newly-activated env — any `#!/usr/bin/env python3`-shebang tool in that target env (e.g. `emu`) then resolves the wrong `python3` and fails with a misleading `ModuleNotFoundError`. Fix: invoke the outer tool (`snakemake`) via its absolute path instead of PATH-prepending its env dir. Full repro/fix in [[PRISM]]'s "ONT/Emu path's phylogenetic tree" section.
- **`list.files(pattern=)` in R only ever matches a file's basename, never its directory path** -- confirmed directly (a path-shaped pattern like `"dir/file\\.tsv$"` matches nothing, even against a real file at exactly that relative path). Caught while fixing a real PRISM bug where a filename ("prism_abundance_table.tsv") is legitimately produced in 3 different places in the same run, and the naive fix (make the regex more path-specific) silently matched zero files instead of the intended one. Real fix pattern: disambiguate AFTER listing every hit (e.g. prefer whichever full path contains a known substring), not by trying to encode a directory into the match pattern. See [[PRISM]]'s "Trees wired into the Plots tab's phyloseq object" section.

## Incidente: limpeza de comentários por regex destruiu 138 arquivos (2026-08-10)

**O que aconteceu.** Para a tarefa de remover comentários de desenvolvimento antes da
publicação, apliquei regexes de linha inteira sobre toda a base de código, em vez de editar
só linhas de comentário. Quatro regras eram destrutivas para *código*, não só para texto:

| Regra | Intenção | Dano real |
|---|---|---|
| `re.sub(r'\(\s*\)', '', s)` | tirar `()` vazios de prosa | removeu **toda** chamada zero-arg do código |
| `re.sub(r'\[\[([^\]]+)\]\]', r'\1', s)` | resolver links `[[wiki]]` das notas | destruiu indexação `[[ ]]` do R e `[[...]]` do pandas |
| `re.sub(r'(#\|--\|//)\s{2,}', r'\1 ', s)` | normalizar espaço após marcador | engoliu a linha de código seguinte para dentro do comentário |
| `re.sub(r'\s+([,.;:])', r'\1', s)` | tirar espaço antes de pontuação | juntou linhas que começavam com `.`, `,`, `:` ou `...` |

A pasta **não era versionada** — fato que eu mesmo tinha registrado na limpeza do dia
anterior — e mesmo assim não fiz backup antes. Não havia como reverter.

**Como foi reparado.** `git init` + commit do estado danificado como ponto de restauração,
push para repositório privado, e então reversão sistemática por linguagem, cada etapa
verificada por parser/compilador real em vez de inspeção visual:

- **Dart** — 1179 problemas → 0 erros; `flutter build linux --debug` compila.
- **Python** — 0 erros de compilação, `pyflakes` limpo. 39 chamadas zero-arg restauradas.
- **R** — 47 scripts parseiam; ~180 sítios corrigidos.
- **Snakemake** — 44 arquivos compilam pelo parser do próprio Snakemake.

**Detectores construídos (reutilizáveis).** Grep não acha esse dano, porque o resultado
continua sintaticamente válido. O que funcionou foi análise estática semântica:

1. **Símbolo indefinido + divisão prefixo/sufixo** — para cada símbolo usado mas nunca
   definido, testar todas as divisões `a+b`; se `a` e `b` forem ambos símbolos reais do
   arquivo, era `a[[b]]`. Achou `metagroup_var` → `meta[[group_var]]`, `setslvl` →
   `sets[[lvl]]`, `partslength(parts) + 1` → `parts[[length(parts) + 1]]`, etc.
2. **Dead store + divisão** — o detector acima é cego para o lado esquerdo de atribuições
   (`args[[key]] <- v` vira `argskey <- v`, que "define" `argskey`). Complemento: símbolos
   atribuídos e **nunca lidos**, também divisíveis. Achou `argskey` no parser de CLI —
   que quebrava *todos* os scripts de análise.
3. **Varredura AST de chamadas zero-arg** — nomes conhecidos como funções usados em posição
   de valor. Achou `uuid.uuid4.hex`, `env=_subprocess_env`, `runs_store.list_runs`,
   `h.hexdigest`, `this_script_dir` (38 sítios), `parse_cli_args`, `list`, `ggplot`,
   `coord_flip`, `scale_x_log10`.
4. **Colchetes vazados para dentro de strings** — nenhum literal legítimo começa com `]]`
   ou termina com `[[`; tudo que casava era dano.
5. **Comentário contendo código** — comentário com `<-`, `@app.`, ou `...ident` colado.

**Validação funcional** (o passo que realmente fechou a conta — os parsers passavam muito
antes do código estar correto): os 5 loaders da aba Plots rodados sobre as runs demo, e as
31 análises implementadas executadas de verdade. 30 produzem saída. A restante (`de_upset`)
para na própria validação de entrada — o dataset DEFINE demo tem só 2 níveis e ela exige
≥ 2 níveis não-referência; o gêmeo `dogma_de_upset`, mesmo código com 3 níveis, passa.

**Regras adotadas daqui em diante.**
1. O projeto agora é um repositório git privado (`oliv-angelus/OmniOmics`) — commitar antes
   de qualquer edição em massa.
2. Nunca aplicar regex de arquivo inteiro para editar comentários. Editar **só linhas de
   comentário**, arquivo por arquivo.
3. Depois de qualquer edição ampla: parser de cada linguagem **e** execução funcional. Só
   parsear não detecta nada dessa classe de dano.
