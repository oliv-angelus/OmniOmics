# DOGMA

Diversity Of Gene expression — Metatranscriptome Analysis. Third pipeline plugged into [[Project Overview|OmniOmics]], after [[MAGMA]] and [[SIGMA]]. Category: `metatranscriptomics` (was already a placeholder card on the Hub before this pipeline existed, per [[Project Overview]]'s roadmap list).

**No `tags` entry** — unlike SIGMA's `["prokaryote"]`, DOGMA initially got the same tag but the user caught that it was wrong: a *meta*transcriptome contains prokaryotic **and** eukaryotic RNA together (soil/environmental communities have both), so "prokaryote" as a pipeline-level tag was misleading. Removed. See the domain-filtering section below for the real (per-run, optional) way this gets handled instead.

Name chosen to fit the MAGMA/SIGMA "-GMA" sound family, and because "the central dogma" (DNA→RNA→protein) is literally what metatranscriptomics studies — the RNA/expression step, as opposed to MAGMA's DNA/presence step.

**Icon: decided.** Three concept drafts were generated matching MAGMA/SIGMA's visual language (dark rounded-square bg, single gradient-stroke glyph, fuchsia/purple gradient matching the `metatranscriptomics` category color) and saved to `build/dogma_icon_concepts/` — A (three connected nodes, abstract DNA→RNA→Protein flow), B (crossed double helix unwinding into a single wave, tying directly to the "central dogma" name origin below), C (a single RNA wave/ribbon, simplest). **User picked C** — now installed as `app/assets/pipeline_icons/dogma.png` (512×512, same size/shape as `magma.png`/`sigma.png`; icon assets here are just one PNG each, referenced as a folder-level Flutter asset in `pubspec.yaml`, no other sizes to generate). The `build/dogma_icon_concepts/` drafts are left on disk as-is (small, harmless) in case the user wants to revisit A/B later.

**Status as of writing: Phase 1 built, including prokaryote/eukaryote read-domain splitting** (QC + rRNA removal + optional taxonomic screening + optional domain split). Built and verified incrementally on purpose, not all at once — see [[Decisions Log]]. **Next up: Phase 2** (assembly onward, decisions already made — see below), not yet implemented.

## What exists so far

- `pipelines/dogma/` — same shape as MAGMA/SIGMA (`Snakefile` + `workflow/rules/*.smk` + `pipeline.yaml`).
- Sample sheet: RNA reads only for now (`short_reads_dir`/`long_reads_dir`, same folder-per-sample convention as MAGMA/SIGMA). The DNA-reads and "reuse an existing MAGMA run" inputs are NOT built yet — that's Phase 2.
- QC: fastp/filtlong, identical to MAGMA/SIGMA.
- **riboDetector** for rRNA removal — chosen over SortMeRNA after a real head-to-head: SortMeRNA 7.0.0 crashed with `SIGILL` (illegal instruction) on this dev machine, a real binary-compatibility problem, not a flag issue. riboDetector installed and ran cleanly, needs no separate reference database (ships a bundled ONNX model), and correctly classified rRNA vs non-rRNA on a real test run (1500 reads → 63 rRNA / 1437 non-rRNA). Runs via `ribodetector_cpu` (not the GPU variant — no other tool in this app depends on CUDA, kept that consistent).
- Split into `ribodetector_short` (paired, `-l 150`) and `ribodetector_long` (single-end, `-l 1000`) rules, mirroring how fastp/filtlong are already split by read type — different `-l` (expected read length) per technology.
- Kraken2 + Kaiju, optional, run on the rRNA-depleted reads (not the raw trim) — same tools/database entries as MAGMA/SIGMA (identical `setting_key`s, so one download covers all three pipelines via the Hub-level Databases screen).

## Prokaryote/eukaryote read splitting — implemented 2026-07-10

**User's ask, verbatim intent**: a metatranscriptome naturally contains both prokaryotic and eukaryotic RNA (e.g. soil communities have bacteria/archaea *and* fungi/protists). The user wants an **optional** choice — analyze prokaryotic reads only, eukaryotic reads only, or both kept separate — not a hard-coded assumption either way.

**Literature grounding (real WebSearch, not assumption) — Tiara is the wrong tool here:**
- Tiara (what MAGMA uses to split prokaryote/eukaryote *contigs* after assembly) needs long sequences to classify reliably — its own docs recommend ≥3000 bp and advise against anything under 1000 bp ([Tiara paper](https://academic.oup.com/bioinformatics/article/38/2/344/6375939), [Tiara GitHub](https://github.com/ibe-uw/tiara)). Individual transcripts (especially prokaryotic genes, no introns, typically 500–1500 bp) and raw reads are mostly shorter than that — Tiara would misclassify a lot of them.
- The established practice for metatranscriptomics is the opposite order from MAGMA: classify **reads** by taxonomic domain **before** assembly, not classify contigs after. See [PMC9983209 (eukaryotic metatranscriptome assembly best practices)](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC9983209/).
- The concrete tool for this is **KrakenTools' `extract_kraken_reads.py`** ([repo](https://github.com/jenniferlu717/KrakenTools), confirmed via its own docs) — takes Kraken2's per-read output + a list of NCBI taxonomy IDs (2 = Bacteria, 2157 = Archaea, 2759 = Eukaryota), supports `--include-children` (catch everything nested below that node) and `--exclude` (invert to "everything except"), handles paired or single-end, gzip or not. This is the *same KrakenTools package* MAGMA already depends on for `kreport2mpa.py` — no new tool family, just a different script from a package already in the stack. Confirmed via the script's own source (`extract_kraken_reads.py` on GitHub) that it always writes **plain, uncompressed** FASTA/FASTQ regardless of the `-o`/`-o2` filename — no auto-gzip — so the new rules write to a `.tmp` plain file then `gzip -c` it into the real `.fastq.gz` output, same as everywhere else in this pipeline gzips its outputs.

**What was built:**
- New manifest tool `domain_filter` in `pipeline.yaml` (category "Contamination Screening"), gated on `kraken2` being active (`requires: [{"tools": ["kraken2"], "min": 1}]` — Kaiju's output isn't Kraken-report shaped, so this tool simply can't run off Kaiju alone; no equivalent was written for Kaiju's format). One flag, `mode`, type `choice`, values `prokaryote` (default) / `eukaryote` / `both` — renders as a normal Tools-tab dropdown, no bespoke UI needed.
- `krakentools` added to `pipelines/dogma/workflow/envs/kraken2.yaml` (same env the `kraken2` rule already uses).
- Two new rules in `02_screening.smk`: `extract_domain_short` (paired short/hybrid reads) and `extract_domain_long` (single-end long reads) — same short/long split convention as `fastp`/`filtlong`/`ribodetector`. Each always declares **all 4 (or 2, for long) output files** (prokaryote + eukaryote) regardless of `mode`, and touches empty placeholders for whichever domain(s) `mode` didn't select — same "touch what doesn't apply" pattern already used throughout `01_qc.smk` for read-type mismatches. Runs on the ribodetector-clean reads (post-rRNA-removal), consuming Kraken2's `.output` + `.kreport`.
- New outputs added as explicit `rule all` targets in the `Snakefile` — nothing downstream consumes them yet (Phase 2/assembly doesn't exist), so unlike ribodetector's output (pulled in transitively as Kraken2/Kaiju's input), these need to be requested directly or Snakemake would never build them.
- `domain_filter`'s `mode` isn't a real CLI flag on any single tool (it drives *which* `extract_kraken_reads.py` invocations run inside the rule's own shell logic), so it's serialized like MAGMA's `mags_annot`: a dict (`{"mode": "prokaryote"}`) merged straight into `config["params"]["domain_filter"]`, not a flag string. `app/lib/screens/launch/launch_screen.dart`'s `_buildAndSaveConfig()` special-cases both tool ids the same way; no other frontend/backend changes were needed since `config_engine.py`'s dict-merge branch and the Tools tab's generic `choice`-flag dropdown already handle everything else generically.
- Verified with a real `snakemake -n` dry-run against a throwaway two-sample (short + long) config (both `mode: both` and `mode: prokaryote`) — confirmed the DAG resolves correctly, Kraken2 → `extract_domain_short`/`extract_domain_long` chains as expected, and the baked-in shell conditionals pick the right branch per mode. Also ran `flutter analyze` on the touched Dart file — no issues.

**Still open**: whatever Phase 2 assembly ends up consuming (once built) needs to read from these domain-filtered outputs *instead of* the plain ribodetector-clean reads *only when `domain_filter` is active* — that wiring doesn't exist yet since Phase 2 itself doesn't exist yet.

## What's next (Phase 2 — not built yet)

Three modes for the assembly/reference step, per the user's original explicit design:
1. Point at an existing MAGMA output folder and reuse its assembly (skip re-assembling).
2. Run metagenome + metatranscriptome together inside DOGMA itself (needs DOGMA to reuse MAGMA's assembly rules somehow — architecture not decided yet).
3. Metatranscriptome only → de novo transcript assembly (mode 3, below, now has a concrete tool decision).

**Superseded 2026-07-30 — modes redefined, see "MAGMA Cross-Reference" section below.** Original modes 1/2 both assumed DOGMA needed to *consume or reuse MAGMA's assembly itself* (skip-assembly or literal co-run), which meant DOGMA would need to invoke/duplicate MAGMA's Snakemake rules — real cross-pipeline coupling nothing else in the app has, and never resolved past "architecture not decided." User's key realization while discussing this: DOGMA is RNA (reverse-transcribed to cDNA) and MAGMA is DNA, so there's nothing to literally "reuse" at the assembly level — the only place a paired metagenome actually helps is *after* DOGMA has its own de novo transcripts, by cross-referencing them against MAGMA's MAGs for genome-resolved taxonomy. New, much simpler design: **mode 1 = de novo assembly** (renamed from the old mode 3 — DOGMA's only mode, already built and complete), **mode 2 = MAGMA Cross-Reference** (new, built 2026-07-30 — DIAMOND blastp of DOGMA's own transcripts against a *finished* MAGMA run's dereplicated MAGs, no MAGMA rule execution or sample-sheet DNA-reads column needed). The old mode 1 (skip-DOGMA-assembly-and-map-reads-to-MAGMA-contigs) and old mode 2 (live co-run) are dropped, not deferred — the new design covers the same paired-metagenome use case without the unsolved architecture problem.

Then: gene prediction/annotation on whichever assembly resulted, taxonomic assignment of transcripts, and expression quantification (Salmon/featureCounts → a raw + TPM-normalized count matrix). **Differential expression (DESeq2/edgeR) is explicitly out of scope** — the user is writing their own R scripts for the Gráficos tab and wants DOGMA to stop at a clean count matrix, not do the statistics itself.

### Literature research done 2026-07-10 (real WebSearch/WebFetch, not assumption) — decisions confirmed with user for Phase 2

Surveyed metatranscriptomics methods papers, mostly 2020–2026, soil/sediment/water focus, to validate/inform Phase 2 tool choices:
- [MT-Enviro benchmark (2025, ISME Communications)](https://pmc.ncbi.nlm.nih.gov/articles/PMC12202999/) — 36-combination benchmark across QC/rRNA/alignment/taxonomy/quantification tools on soil/marine/extreme-environment simulated data. Best-performing combo found: Trimmomatic + RiBase (integrated rRNA DB) + BBMap + TPM. Doesn't invalidate DOGMA's fastp/riboDetector choices (no direct riboDetector comparison exists in literature — a known blind spot, not a contradiction), but confirms TPM > FPKM.
- [PMC9983209 (Reverse engineering environmental metatranscriptomes)](https://pmc.ncbi.nlm.nih.gov/articles/PMC9983209/) — already cited above for the domain-splitting plan. Also source for the multi-assembler-ensemble idea (rnaSPAdes+MEGAHIT+Trinity+metaSPAdes, deduplicated via MMseqs2 at 100%→98% identity into a "MAD" multi-assembler-deduplicated set) and for TransDecoder as the ORF-calling tool on assembled transcripts, EUKulele (vs MMETSP/MarRef) for eukaryotic transcript taxonomy.
- [CoMW (GigaScience, validated on Arctic + temperate **soil**)](https://pmc.ncbi.nlm.nih.gov/articles/PMC6667343) — directly validates DOGMA's decision to assemble at all: assembly-based approach had 0.6% false-positive functional gene calls vs up to 15% for assembly-free (map-reads-to-DB-directly) approaches, in soil-like environments specifically. Also the source for CAZy/NCycDB as soil-relevant specialized functional annotation databases (carbon/nitrogen cycling genes), on top of eggNOG-mapper.
- [ISME Journal 2025 — case for absolute gene expression](https://academic.oup.com/ismej/article/19/1/wraf188/8239678) — argues TPM is compositional (one taxon spiking suppresses everyone else's TPM even if their real abundance/activity didn't change) and proposes RNA spike-in standards (ERCC/sequins, ~1% of extracted RNA, ideally added before extraction) converted via a per-sample linear model into TPL (transcripts per liter) for true cross-sample comparability. This is a wet-lab protocol dependency, not something bioinformatics alone can retrofit after the fact.

**Decisions made with user from this research (2026-07-10), for whenever Phase 2 assembly/annotation is actually built:**
1. **Multi-assembler ensemble + MMseqs2 dedup**, not single rnaSPAdes — rnaSPAdes + MEGAHIT + Trinity, deduplicated per PMC9983209's approach. Chosen over the simpler single-assembler default despite ~3x runtime/complexity cost, because no single assembler is universally best (rnaSPAdes maps best individually at 75.0±4.7% but MEGAHIT/Trinity recover different genes).
2. **No co-assembly** (pooling reads across samples before assembly) — stays per-sample only, consistent with how MAGMA/SIGMA already work. Revisit only if a real use case needs recovering very-low-abundance genes across replicates from the same site/season.
3. **CAZy and NCycDB added as optional extras** alongside eggNOG-mapper for functional annotation — soil/sediment biogeochemistry (carbon/nitrogen cycling) relevance per CoMW, same "optional extra on top of the default annotator" pattern SIGMA already uses for eggNOG-mapper itself. **Expanded 2026-07-27** (user felt C+N alone was too narrow, explicitly asked for more): added SCycDB (sulfur), MCycDB (methane), and CANT-HYD (hydrocarbons) + FeGenie (iron) as further optional extras — see the "Phase 2 step 3 (expanded)" section below for the real research/verification behind each. **PCycDB (phosphorus) was researched but not implemented** — its GitHub repo (the paper's own stated data-availability location) only ships post-processing scripts, not the actual reference database; confirmed by reading the paper's data-availability statement directly, which itself just points back to the same repo and recommends emailing the authors. Revisit only if the user wants to pursue that manually.
4. **Spike-in RNA quantification**: not implementing TPL calculation now (needs a real wet-lab spike-in protocol the user would have to adopt first), but **add an optional spike-in concentration field to the sample sheet schema now** so it doesn't require a schema migration later if/when this gets implemented. Salmon/featureCounts → TPM remains the actual computed output for now.

### Phase 2 mode-3 (de novo assembly) — first increment built + dry-run verified 2026-07-25

The multi-assembler ensemble + MMseqs2 dedup is implemented for **short/hybrid** samples:
- New rules in `workflow/rules/03_assembly.smk`: `rnaspades`, `megahit`, `trinity` (all paired short-read, reading the ribodetector-clean reads `results/01_QC/{sample}/{sample}_R{1,2}_clean.fastq.gz`), and `transcript_set` (combines the active assemblers' transcripts with source-prefixed headers, then `mmseqs easy-linclust` → the "MAD" set `results/03_ASSEMBLY/{sample}/{sample}_transcripts_mad.fasta`).
- New envs: `rnaspades.yaml` (spades=3.15.5, same pin as MAGMA — rnaspades.py ships with SPAdes), `megahit.yaml` (megahit=1.2.9), `trinity.yaml` (trinity=2.15.1), `mmseqs2.yaml` (mmseqs2=15.6f452).
- Manifest: new category "Assembly"; 4 new tools (`rnaspades`/`megahit`/`trinity` each `requires` ribodetector≥1; `transcript_set` `requires` ≥1 of the three assemblers); defaults (`trinity`: `--max_memory 50G`; `transcript_set`: `--min-seq-id 0.98 -c 0.9`) + default_threads. Snakefile: `SHORT_SAMPLES` + the MAD target in `rule all` + the include.
- **Key design (verified):** each assembler is an independently toggleable tool; `transcript_set`'s input is a function keyed on `config["active_tools"]`, so it stays consistent with the client's `--omit-from` — disabling one assembler shrinks the ensemble instead of breaking dedup (dry-run confirmed: trinity off → transcript_set combines only rnaspades+megahit, trinity not built). Full `rule all` dry-run with faithful `--omit-from` resolves to 12 jobs for 2 short samples (fastp→ribodetector→{rnaspades,megahit,trinity}→transcript_set).
- **NOT yet done / caveats for this increment:** (a) domain-filter input wiring still not done — assembly always reads plain ribodetector-clean reads, even when `domain_filter` is active (should read the 02_SCREENING domain-split reads then); (b) long-read-only metatranscriptome assembly has no assembler (all three are short-read) — separate undecided design question; (c) the PMC9983209 100%→98% two-step dedup is approximated by a single `--min-seq-id 0.98` linclust for now.

**Smoke test — real execution 2026-07-25 (on the user's Ryzen 7 5700U / 8 GB laptop).** Ran the actual conda envs + shell commands on a synthetic 1707-pair / 20-transcript dataset (reads pre-placed as `_R{1,2}_clean.fastq.gz`, `--allowed-rules` to isolate assembly from QC), Trinity `--max_memory` lowered to 2G. Results:

  - **rnaSPAdes env fix required:** the original `spades=3.15.5` pin (mirrored from MAGMA) **fails on this machine** — SPAdes 3.15.5's Python scripts `import distutils`, removed in py3.12 and not reliably shimmed by the modern conda-forge python/setuptools 83 installed today (`ModuleNotFoundError: No module named 'distutils'`). Bumped `rnaspades.yaml` to `spades=4.3.0` (distutils-free), which fixed it. NOTE: MAGMA/SIGMA still pin `spades=3.15.5` and would hit the same failure if their spades rules were run on current packages — pre-existing latent issue, not touched (out of scope, they're "stable"), but worth flagging.
  - **Trinity NOT validated — its conda env won't install here.** `trinity=2.15.1` pulls a heavy R/Bioconductor DE-analysis stack (which DOGMA doesn't even use — DE is out of scope) and the `bioconductor-genelendatabase` **post-link script fails** (`LinkError`), aborting env creation. Also the heaviest tool to actually *run* on an 8 GB laptop. **Decision (user, 2026-07-25): keep Trinity available but off by default** — rnaSPAdes+MEGAHIT is the working default 2-assembler ensemble; Trinity is opt-in for users with a working env/hardware. Implemented via a new generic manifest field `active_by_default` (defaults true; set `false` on DOGMA's `trinity`). Frontend: new `ToolDef.activeByDefault` (`models/tool.dart`); `launch_screen.dart` now seeds `_activeTools` from tools where `activeByDefault` instead of all tools. `transcript_set`'s `requires` (≥1 of the 3 assemblers) stays satisfied, and with Trinity inactive the client `--omit-from`s it + the dedup input function excludes it (already verified). `flutter analyze` clean.

### Phase 2 step 2 (ORF calling — TransDecoder) — built + dry-run + real smoke-tested 2026-07-27

New rule `transdecoder` in `workflow/rules/04_orf_calling.smk` (new file, new phase), taking the MAD transcript set (`results/03_ASSEMBLY/{sample}/{sample}_transcripts_mad.fasta`) → `results/04_ORF_CALLING/{sample}/{sample}_transdecoder.{pep,cds,gff3,bed}`. New env `transdecoder.yaml` (`transdecoder=5.7.1`, current bioconda version — installs cleanly, unlike Trinity's env; pulls a light R/ggplot2 stack for its optional PWM plots but that's cosmetic, no post-link failures). Manifest: new category "ORF Calling" (confirmed generic — no Flutter/backend code special-cases category strings, verified via Explore agent before adding); new tool `transdecoder` (`requires` `transcript_set`≥1, empty `flags`/`""` default `extra`, matching the minimal-flags pattern already used for rnaspades/megahit rather than inventing an unrequested UI toggle); `default_threads.transdecoder = 1` (TransDecoder.LongOrfs/.Predict have no multithreading option — same `threads: 1` + comment pattern as `kaiju_table`/`extract_domain_*`). Applies to `SHORT_SAMPLES` only, same scope as assembly (TransDecoder runs on the MAD set, which only exists for short/hybrid samples).

**Design note — same "tool writes into cwd off the input's basename" problem Trinity has:** TransDecoder.LongOrfs/.Predict write outputs (and a working `*.transdecoder_dir/`) into the current working directory, named after the input file's basename — running that directly in the shared pipeline root would collide across samples executing in parallel. Solved the same way as the Trinity rule: a per-sample scratch dir (`results/04_ORF_CALLING/{sample}/transdecoder_work/`), a symlink of the MAD fasta into it as `transcripts.fasta`, `cd` in, run both TransDecoder steps, `mv` the four real outputs out to their declared paths, then `rm -rf` the scratch dir.

**Verification:**
- `snakemake -n` dry-run (real `snakemake=9.23.1` from the repo's `snakemake` conda env, not just code review) against a minimal fixture (1 short sample, placeholder empty FASTQs) — targeted dry-run resolves the full chain `fastp→ribodetector_short→{rnaspades,megahit}→transcript_set→transdecoder` correctly; full `rule all` dry-run (14 jobs) also resolves clean with `transdecoder` included, nothing else broke.
- **Real execution smoke test:** built a throwaway `transdecoder=5.7.1` conda env (installed clean, ~1-2 min, no env issues at all — unlike Trinity), generated a small synthetic transcript FASTA (446 nt: random 5'/3' UTR-like flanks around a planted 121-aa ORF with no internal stop codons), and ran the rule's actual shell logic (not a paraphrase) end-to-end outside Snakemake. Result: exit 0, TransDecoder found a real ORF (134 aa, 5'-partial — found for the whole planted ORF plus more upstream in-frame sequence, which is correct/expected default behavior), all four output files (`.pep`/`.cds`/`.gff3`/`.bed`) produced with real, valid content, the `mv`s all succeeded, and the scratch `transdecoder_work/` dir was cleaned up (nothing left behind). Throwaway env + scratch fixtures removed after.
- **Not yet exercised:** a full real-length transcriptome (thousands of transcripts) on the user's 8 GB laptop — the synthetic single-sequence test validates correctness/wiring, not runtime/memory at scale. TransDecoder is lightweight compared to the assemblers, so this is a low-risk gap, but worth a real run once the pipeline reaches functional annotation and there's a full transcript set to push through anyway.
- **No functional-annotation/homology evidence wired in** (no `--single_best_only`, no `--retain_pfam_hits`/`--retain_blastp_hits`) — matches the "no decisions made on this yet" state; `transdecoder`'s `extra` params field is exposed empty so this can be added later (e.g. once eggNOG-mapper/Pfam are wired) without a rule change.

### Phase 2 step 3 (functional annotation — eggNOG-mapper + CAZy + NCycDB) — built + verified 2026-07-27

New rule file `workflow/rules/05_annotation.smk`, all three reading TransDecoder's `.pep` output (`results/04_ORF_CALLING/{sample}/{sample}_transdecoder.pep`) → `results/05_ANNOTATION/{sample}/...`. All three apply to `SHORT_SAMPLES` only (same scope as everything downstream of the MAD set).

**eggNOG-mapper (default annotator), `eggnog_sample`:** byte-identical invocation pattern to MAGMA's/SIGMA's existing `eggnog_sample` rules (`emapper.py -m diamond ...`), same `eggnog.yaml` env pin (`eggnog-mapper=2.1.13`) and manifest `flags`/`databases.eggnog` block (copied, not re-derived — same eggnog5.embl.de DB, ~14 GB). Only difference from MAGMA/SIGMA: reads TransDecoder's `.pep` instead of Prodigal's/Bakta's. ### Domain-filter wiring, long-read assembly, and two-step dedup — 2026-07-27

**Two-step dedup — done, real params from the source paper's own code, not the prose.** The paper (PMC9983209) turned out to be Krinos, Cohen, Follows & Alexander (2023), *BMC Bioinformatics* 24:93, describing the **eukrhythmic** pipeline (github.com/AlexanderLabWHOI/eukrhythmic). Fetched their actual Snakemake rules (`07-CAG.smk`, `12-MAD.smk`), not just the methods prose, since the prose alone ("100%→98%") doesn't give exact flags. Real procedure: **step 1** clusters at 100% identity to collapse contigs multiple assemblers independently recovered *identically*; **step 2** then clusters the step-1 output at 98% identity to additionally collapse near-identical contigs (sequencing-error-level variation) that step 1 alone wouldn't catch. Both steps use `--cov-mode 1 -c 0.98` (previously DOGMA's single-pass approximation used `-c 0.9`, missing the coverage mode entirely and the two-stage structure). eukrhythmic runs step 1 per "assembly group" then step 2 once globally across every sample/group pooled together; DOGMA has no co-assembly step (strictly per-sample, a deliberate earlier decision — see the Phase 2 literature-decisions section above), so both steps now run per-sample here, preserving the paper's two-stage *structure* at DOGMA's actual working granularity rather than its exact multi-sample scope (which doesn't apply). New manifest param `transcript_set_step1` (`--min-seq-id 1.00 --cov-mode 1 -c 0.98`) alongside the existing `transcript_set` key, now updated to `--min-seq-id 0.98 --cov-mode 1 -c 0.98` for step 2. **Real end-to-end verification**, not just dry-run: built a real `mmseqs2=15.6f452` env (matching the pipeline's own pin), generated synthetic multi-assembler output with three known cases — an exact duplicate (100% identical to another sequence), a near-duplicate (3 point mutations, ~99% identity), and a genuinely unique sequence — and ran the exact two-step shell logic. Result matched the paper's design precisely: the exact duplicate collapsed at step 1 (5→4 sequences), the near-duplicate correctly *survived* step 1 (not 100% identical) but collapsed at step 2 (4→3 sequences), and the unique sequence survived both steps. This confirms the two-step design does something the single-step 0.98-only approach couldn't: separately guarantees exact-duplicate removal is unaffected by coverage-mode/other-flag choices tuned for the near-duplicate pass.

**Not yet done:** none of these three items have a real multi-GB-scale smoke test (the earlier Phase 2 mode-3 smoke test's synthetic dataset would need regenerating with domain-split reads to exercise the new wiring with real assemblers end-to-end) — the dry-run + isolated real-mechanism tests above are the verification bar met here, consistent with how kraken2/kaiju/eggnog-scale work has been verified throughout Phase 2.

### Phase 2 step 5 (quantification — Salmon) — built + real end-to-end verified 2026-07-28

**Salmon-vs-featureCounts design question resolved via real research, not the original "Salmon/featureCounts" shorthand taken literally.** User asked directly why both were named together before agreeing to implement anything. **User's decision: don't build this into DOGMA — do the merge later, at the plotting stage, in R.** Explicit reasoning given: a bigger, more careful, purpose-built script written at analysis time carries less risk than a generic merge baked into the pipeline now — avoids a badly-designed join silently corrupting or mixing up results that get baked into every downstream run. **This is a real, deliberate scope boundary, not an oversight** — DOGMA's contract stays "produce the per-tool tables, stop there," matching the already-established DESeq2/edgeR-out-of-scope precedent (user does the statistics/integration work in their own R scripts, not the pipeline). ## MAGMA Cross-Reference (mode 2) — designed, prototyped, and built 2026-07-30

**Redesign of the old modes 1/2 (see the superseded note in "What's next" above).** Talking through the original design with the user surfaced the real reason it never got built: DOGMA is metatranscriptome (RNA reverse-transcribed to cDNA) and MAGMA is metagenome (DNA) — there is no assembly-level artifact to literally "reuse" between them, so the old mode 1 (skip DOGMA's own assembly, map reads straight to MAGMA's contigs) and mode 2 (co-run both inside DOGMA) were both solving a problem that doesn't actually exist, at the cost of a real one (DOGMA invoking or duplicating MAGMA's Snakemake rules — cross-pipeline coupling nothing else in the app has). **Tool/method choice, discussed explicitly for publication robustness (user's framing: "para deixar o artigo do app bem robusto")**: DIAMOND protein-vs-protein search of DOGMA's TransDecoder proteins against every dereplicated MAG's own Prodigal/Pyrodigal-predicted proteins from the paired MAGMA run, joined to that MAG's GTDB-Tk taxonomy call. ## Plots tab: the merge, finally built (2026-08-07) — a real third `input_shape`, `dogma_annotated`

User asked to start Plots-tab support for DOGMA. This is the merge step explicitly deferred above ("do the merge later, at the plotting stage, in R") — now built, exactly per that earlier design, not reopened/reconsidered. Real column shapes for all ~10 files (not guessed from the shell commands alone) were confirmed 2026-08-07 by installing DOGMA's own pinned tool versions for real and reading their actual source/output.

**Two-stage design, mirroring the DEFINE precedent but genuinely different underneath:**
1. **`plots/scripts/lib/build_dogma_table.R`** — `build_dogma_table(results_dir)` discovers every real sample x domain from TransDecoder's own `.pep` files (the one output every Phase-2-active sample is guaranteed to have), then for each one LEFT JOINs every present annotation table onto the ORF spine (eggNOG, CAZy, NCycDB/SCycDB/MCycDB, CANT-HYD, FeGenie, EUKulele) plus two transcript-keyed ones broadcast down to their ORFs (Salmon `quant.sf`, CAT/BAT). A missing file (tool wasn't active) contributes no columns at all; an empty-but-present file (tool ran, found nothing) is an empty join, same effective result. Real, load-bearing design choice for `domain_filter`'s `mode=both`: since that mode keeps prokaryote/eukaryote genuinely separate by DOGMA's own earlier decision, the merged table folds `{sample, domain}` into one composite `sample_domain` key (`sample1__prokaryote`) whenever more than one domain exists in a run, so downstream analyses never silently mix two different assemblies' expression under one sample name.
2. **`aggregate_dogma_counts()`** (same file) — the real bridge that makes cross-sample comparison possible at all: DOGMA has no co-assembly (per-sample only), so raw ORF/transcript IDs are never comparable across samples, exactly the scope note already on record above. Sums Salmon read counts per chosen functional-annotation category (KEGG ortholog, COG category, a cycling-gene family, ...) per sample instead — the same real, literature-established fix CoMW (already cited above) uses. Returns the *exact* `list(counts=, gene_info=, coldata=)` shape `build_count_matrix.R` returns, so DEFINE's existing `deseq_helpers.R` (`run_deseq()`, `deseq_coef_name()`, `vst_blind()`) works against it completely unchanged — no DESeq2 logic duplicated.

**New loader `plots/scripts/load_dogma_table.R`** (mirrors `load_phyloseq.R`/`load_count_matrix.R`): builds the long table once, joins real sample metadata (replicated per domain + a synthetic `domain` column added when `mode=both`), caches `dogma_table.rds`, reports a curated whitelist of "real gene-family/grouping" columns actually present in the run (`DOGMA_ANNOTATION_COLUMNS` — raw per-hit stats like evalue/bitscore are deliberately excluded, they're not meaningful group-by keys).

**Two new analyses** (`plots/manifest.yaml`, `applies_to: [dogma]`, `input_shape: dogma_annotated`):
- `dogma_functional_composition` — stacked relative-abundance bars by a chosen annotation category, the functional analogue of `taxonomic_composition.R` (same shape/intent, un-annotated ORFs kept as an explicit "Unclassified" bucket rather than dropped, matching that script's own convention).
