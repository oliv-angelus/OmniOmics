# Decisions Log

Chronological, most-load-bearing decisions from building [[Project Overview|OmniOmics]] out of the original `MAGMA-ideia-de-app` Electron prototype.

## Architecture
- **Kept the FastAPI/Python backend, rewrote only the frontend** (Electron+HTML → Flutter native). The backend's hard-won logic (conda/snakemake install, DB downloads, Snakemake log parsing) was ported near-verbatim, just generalized to be pipeline-agnostic via the [[Pipeline Manifest Schema]] instead of MAGMA-specific hardcoded Python dicts.
- **`--omit-from` over a hand-rolled skip engine**: when the user proposed using Snakemake's own `--omit-from RULE [RULE...]` flag to cascade-disable tools, this turned out to be the right call — it uses Snakemake's real DAG, so correctness doesn't depend on the app's own (necessarily approximate) dependency model. See [[Pipeline Manifest Schema]].
- **Database settings are global, not per-pipeline** — reference DBs (CheckM2, GTDB-Tk, etc.) will likely be reused by future omics pipelines; namespacing them per-pipeline would force redundant downloads.
- **Riverpod gotcha (real bug, cost real debugging time)**: never nest a conditional `ProviderScope` inside a `StatefulWidget.build()` to "wait for async init then override a provider." A parent rebuild (e.g. the theme toggle) can recreate the inner container and drop the override, throwing "must be overridden." Fixed by calling `runApp()` exactly once for the real app, after boot resolves, with a single root `ProviderScope` (see `app/lib/main.dart`).

## Real bugs found and fixed along the way (not just UI polish)
- Two WebSocket routes (`/ws/install/conda`, `/ws/install/snakemake`) were **accidentally dropped** when generalizing `main.py` from the prototype — caught by auditing all 19 original routes 1:1 against the new set, not by testing alone.
- `uvicorn` needs the `websockets` package explicitly (`pip install uvicorn` alone doesn't pull it in) — without it every WS endpoint fails silently with "Unsupported upgrade request."
- PyInstaller-frozen binaries: `__file__`-relative path resolution breaks (resolves inside the temp extraction dir, not the real binary location). Fixed in `backend/pipelines.py` by branching on `sys.frozen`.
- The `.deb`'s `Depends: conda | miniforge3` blocked installation entirely via `dpkg`/gdebi, because conda isn't a real apt/dpkg package — changed to `Recommends`, which the app's own in-app dependency gate makes redundant anyway.
- Anaconda3's download URL has no "-latest-" alias (unlike Miniconda/Miniforge) — a stale/404'd URL returned an HTML error page that bash then choked on as a syntax error. Added a "does this look like a real installer" sanity check (`head.startswith(b"#!")`) before executing any downloaded installer script, to fail with a clear message instead of a cryptic one next time this happens with any distro.
- `binette` hard-required all 4 binners in the actual Snakemake rule — the user's mental model was "at least 2," which is now true after editing `05_mag_refine.smk`.
- **Translation gaps found when the user reported EN mode still showing Portuguese "principalmente nas abas dentro dos pipelines"**: two real leaks inside the pipeline Launch screen tabs — (1) `_inputDirLabel()` in `launch_screen.dart` only special-cased `short_reads_dir`/`long_reads_dir` through `app_strings.dart`; SIGMA's `reference_dir` label fell through to the raw (Portuguese-only) manifest string in `pipeline.yaml`, always showing PT regardless of app language. Fixed by adding an `input_reference_dir` key and a third switch case. (2) `DependencyGraph.missingRequirementLabel()` (`tool_dependency_graph.dart`) hardcoded the `"mín."` abbreviation with no English form, leaking into the "Requires: ..." caption on blocked tools in the Ferramentas tab; fixed by threading an `english` bool through from `ToolCategorySection`. ## Naming
- Hub name: **OmniOmics** (corrected from "Ominiomics," which read as a typo of omni-omics).
- Pipeline keeps the name **MAGMA** — deliberate, to preserve existing brand/icon equity even though the "Metagenome Assisted GUI" backronym no longer fits (it's a pipeline inside a hub now, not its own GUI). Nobody has picked a new backronym yet.
- Second pipeline named **SIGMA** ("Single Isolate Genome, Multi-platform Assembly") — chosen to rhyme with MAGMA after rejecting several rock/mineral-themed names; see [[SIGMA]].
- Fifth pipeline (amplicon sequencing, 16S/18S/ITS metabarcoding) named **PRISM** (2026-08-06) — chosen over several other candidates the user rejected as forced/arbitrary-sounding (an early `ENIGMA`/`AMALGAMA` pass, then a `SIEVE` candidate dropped when its own letter-by-letter breakdown didn't actually spell "SIEVE" in order — user caught this directly). Confirmed correct letter-by-letter this time: **P**rofiling **r**RNA (the marker gene: 16S/18S/ITS) **I**nference (the term DADA2's own paper, Callahan et al. 2016, uses for ASV-calling: "high-resolution sample inference") of **S**pecies (taxonomic resolution) via **M**etabarcoding. Metaphor: a prism resolves mixed light into its component spectrum, same as the pipeline resolves a mixed environmental sample into its component taxa. `CENSUS` (Community/Ecological/Nucleotide/Sequencing/Universal-primers/Species) was the other finalist, also letter-verified correct, not chosen. **Explicit user instruction going forward**: every new pipeline name needs real, non-forced meaning (a genuine acronym mapping to real capabilities and/or a real scientific-concept callback) — confirm the letter order actually spells the name before presenting it, this is exactly what went wrong with the dropped SIEVE candidate.
- **PRISM built long-read-only, by explicit user scope decision (2026-08-06)** — not short-read/hybrid like SIGMA. Design pending real literature review (see [[Known Issues and Next Steps]]) before any manifest/rules are written, same "research first" discipline DOGMA's assembly-ensemble and taxonomy-tool choices followed.

## SIGMA: reference-based assembly, not variant calling
- User wanted a "de novo vs. reference" assembly option in SIGMA. First proposal was Snippy (variant calling → consensus FASTA) as a separate side-output category. User explicitly rejected this: **"na verdade não quero incluir isto de chamada de variantes no pipeline por em quanto. O meu foco não será epidemiologia por agora."**
- Correct tool for "reference-based **assembly**" (not variant calling) is **RagTag** — homology-based scaffolding/reordering of already-assembled contigs against a reference, no consensus-calling involved. Integrated directly into `03_polish.smk`'s `finalize_polish` as an alternate path, gated by an optional `reference_dir` input (same folder-per-sample convention as reads) — a sample with a matching reference folder gets scaffolded, one without just gets the normal polished assembly. Fully mixable: short/long/hybrid read types and with/without-reference are independent per-sample choices, verified together in one dry-run.

## Prodigal → Pyrodigal (MAGMA + SIGMA gene calling)
- User found that Prodigal's `-p meta` mode was deprecated (now `anon`) and that Prodigal itself hasn't been updated since 2016, vs. Pyrodigal being actively maintained with 2026 updates. Verified via real conda-env testing (not just reading docs) before switching: byte-identical calls to Prodigal v2.6.3, real multithreading via `-j` (Prodigal itself has none), near drop-in CLI.

- eggNOG-mapper stays mandatory-ish for MAGMA (metagenomes: Bakta's single-organism assumption doesn't hold), but is an **optional extra** in SIGMA (Bakta alone already covers standard annotation; eggNOG adds deeper KEGG/COG/GO for comparative work).

## Real bugs found and fixed (SIGMA + later session, same bar as the section above)
- **SIGMA's dependency graph had a real gap, not just a UI nit**: unlike MAGMA (where every analysis tool chains back to an assembler via `tiara`), most of SIGMA's downstream tools (QUAST, CheckM2, GUNC, GTDB-Tk, Bakta, ABRicate, VFDB, ISEScan, MOB-suite, MLST, antiSMASH, RagTag, Bowtie2, minimap2) had **no `requires` back to unicycler/flye** in `pipeline.yaml`. Turning off assembly left them showing as active in the UI, and a real run would have failed mid-way with Snakemake's `MissingInputException` once it reached a rule needing contigs that were never assembled. Found by the user actually trying it. Fixed by adding the `{"tools": ["unicycler","flye"], "min": 1}` group to all 14; verified by reimplementing the client-side `settle()` cascade in a Python script against the fixed manifest (only `fastp`/`filtlong` survive disabling both assemblers) and confirming with a real `snakemake -n` dry-run. See [[SIGMA Dependency Graph]].
- `config_engine._write_tsv()`'s `csv.DictWriter` defaults to `extrasaction="raise"`. `build_samples()` started unconditionally adding a `"reference"` key to every row (for SIGMA's RagTag support) — broke MAGMA's `/samples/generate` with a bare 500, since MAGMA's manifest doesn't declare that column. Fixed with `extrasaction="ignore"`.
- `/api/pipelines/{pid}/samples/generate` lacked the try/except-with-`detail` wrapping that `/config/generate` already had, so the bug above surfaced as a generic, undiagnosable 500 instead of a real error message. Added for parity — this is what let the DictWriter bug above actually get diagnosed quickly once it recurred.
- GTK header bar: `gtk_header_bar_set_show_close_button(TRUE)` alone doesn't guarantee minimize/maximize also appear — depends on the desktop's own `button-layout` preference (many default GNOME setups only show close). Fixed by explicitly setting `gtk_header_bar_set_decoration_layout(header_bar, "menu:minimize,maximize,close")`.

## Exporting the pitch deck (Playwright + Chromium, not a print stylesheet)
- No screenshot tool was available in this sandbox (`gnome-screenshot`/`grim`/`flameshot` all absent; GNOME's D-Bus `Screenshot` API returned `AccessDenied`). Worked around it by forcing the Flutter app through XWayland (`GDK_BACKEND=x11`), capturing with `xwd` (the one X11 tool that *was* present), and converting XWD→PNG with a small hand-written parser (Pillow has no XWD plugin). To click through screens for different captures without `xdotool`/`ydotool`, installed `python-xlib` and drove clicks via XTest fake input, re-reading the window's position via `xwininfo -id` before every click since the WM repositions it between actions.
- First PDF export attempt used a `@media print` stylesheet + Chromium's native paginated `page.pdf()`. Two real bugs surfaced: (1) CSS Grid items that need to move to the next printed page can render into empty space instead of the page itself — fixed by switching grid containers to block layout under `@media print`; (2) the actual root cause of missing images was **`loading="lazy"` on `<img>` tags never triggering during headless PDF rendering** for anything below the initial fold — removed it. Both fixes together didn't satisfy the user (content still looked cramped/cut across A4 pages).
- Final approach abandoned print pagination entirely: a Playwright script screenshots each `<section>` individually (`clip` + `full_page=True` so off-screen sections are still capturable), then Pillow scales each capture down to fit a uniform 1280×720 slide (never cropping, letterboxed with the section's own background color) and assembles one PDF page per slide. Better default for "export this page as a deck" than fighting print-CSS page-break semantics.

## Kaiju added alongside Kraken2 (MAGMA), and both added fresh to SIGMA
- User's framing: Kraken2 and Kaiju both only need clean reads, don't depend on each other, so there's no reason to force a single choice — expose both as independently toggleable tools, same as everything else. Implemented that way: `kaiju`'s `requires` is `fastp OR filtlong`, same group as `kraken2`'s, no dependency between the two tools themselves. Verified independence directly — a dry-run with only Kaiju active runs no Kraken2/Bracken jobs, and vice versa.
- Kaiju is protein-level (translated six-frame search against a protein DB), not k-mer/nucleotide like Kraken2 — its output shape is genuinely different (`kaiju2table`'s summary table, not a Kraken-style `.kreport`), so it could NOT just reuse Bracken/kreport2mpa. Gets its own chain instead: `kaiju_classify` → `kaiju_table` (`kaiju2table` at species rank + `kaiju-addTaxonNames` for a human-readable per-read file) → (MAGMA only) `consolidate_taxonomy_kaiju`, mirroring `consolidate_taxonomy`'s cross-sample table but reading Kaiju's own per-sample summaries.
- Real download URLs for Kaiju's pre-built databases (`kaiju-idx.s3.eu-central-1.amazonaws.com`) were fetched live from the project's own downloads page, not guessed — same standard as every other database URL in this manifest. Picked RefSeq (37 GB, complete-genome assemblies) as the recommended default, plus 6 smaller/larger alternatives (representative-only, proGenomes, nr, fungi, viruses-only, plasmids-only).
- **This is also what closed the "SIGMA has no pre-assembly contamination check" gap** flagged right before this: added a new "Contamination Screening" category to SIGMA with both Kraken2 (classify + `.kreport` only, no Bracken — a single isolate doesn't need community-abundance re-estimation, just "does this look like one clean organism") and Kaiju, in a new `12_screening.smk` reusing the exact same `setting_key`s as MAGMA's (`db_kraken2`, `db_kaiju`) so both pipelines share one database download via the Hub-level Databases screen.
- No Dart/Flutter code changed for any of this — confirms the manifest-driven architecture holds not just for adding a *pipeline*, but for adding *tools to an existing pipeline* too. Only `pipeline.yaml`, new `.smk` rule files, and new `envs/*.yaml` were touched; the Tools tab, Resources tab, and Hub-level Databases screen all picked the new tools/database up with zero UI code changes. **Caught the manifest-cache gotcha again while testing this** (`backend/pipelines.py`'s `_cache` doesn't reload on its own) — restarting the backend after any `pipeline.yaml` edit is required before a dry-run will see it; this is now the second time this exact gotcha has cost debugging time in one session, worth remembering by heart going forward.

## DOGMA: third pipeline, built incrementally on purpose
- User confirmed the name **DOGMA** (Diversity Of Gene expression — Metatranscriptome Analysis) — chosen for the MAGMA/SIGMA "-GMA" sound family and the "central dogma" (DNA→RNA→protein) callback, which is literally what metatranscriptomics adds on top of MAGMA (expression, not just presence).
- Explicit user decision: **differential expression (DESeq2/edgeR) stays out of DOGMA's scope.** The user is writing their own R scripts to feed the (still-in-progress) Gráficos tab, and wants DOGMA to stop at a clean count matrix rather than embed statistical comparisons. Revisit only if asked — this was a deliberate scope cut, not an oversight.
- Explicit user decision: **agreed to build incrementally ("refinando com o tempo") rather than fully specifying the pipeline before writing any code.** First slice built and verified: QC + rRNA removal + optional Kraken2/Kaiju screening. The harder part — the 3-mode assembly/reference step (reuse an existing MAGMA run / co-assemble metagenome+metatranscriptome inside DOGMA / metatranscriptome-only de novo) — is deliberately deferred to a later round rather than designed speculatively now. See [[DOGMA]] for the full status and what's next.
- **riboDetector chosen over SortMeRNA after a real test, not by reputation**: SortMeRNA 7.0.0 segfaulted (`SIGILL`) on this dev machine — a genuine binary-compatibility issue. riboDetector installed and ran cleanly with no separate database to download (bundled ONNX model), verified end-to-end on real test data (1500 reads → 63 rRNA / 1437 non-rRNA correctly split). Runs as two rules (`ribodetector_short`/`ribodetector_long`, paired vs single-end, different `-l` expected-length values) rather than one, mirroring how fastp/filtlong are already split by read type in every pipeline so far.
- **DOGMA's initial `["prokaryote"]` tag (copied from SIGMA's pattern) was wrong and got removed.** User caught it: a *meta*transcriptome inherently contains both prokaryotic and eukaryotic RNA (e.g. soil communities), so tagging the whole pipeline "prokaryote" was misleading. Correct fix isn't a different tag, it's a **per-run optional choice** (prokaryote-only / eukaryote-only / both together) — see [[DOGMA]] for the full design, not yet implemented as of this entry.
- **Tiara is the wrong tool for prokaryote/eukaryote separation in DOGMA — confirmed via real literature search, not assumption.** Tiara (MAGMA's contig-classification tool) needs long sequences (its own docs: ≥3000 bp recommended, <1000 bp discouraged) to classify reliably; individual transcripts/reads in metatranscriptomics are mostly shorter than that (prokaryotic genes especially, 500–1500 bp, no introns). The literature's actual standard practice inverts MAGMA's order: classify **reads** by taxonomic domain *before* assembly (not contigs after). Concrete tool: KrakenTools' `extract_kraken_reads.py` (same package MAGMA already uses for `kreport2mpa.py`) — extracts/excludes reads by NCBI taxid with `--include-children`, on Kraken2's existing per-read output. Full plan and citations in [[DOGMA]]'s "Next task" section — this is the confirmed next thing to build.
- **Domain split implemented (2026-07-10)**, closing the item above: new `domain_filter` manifest tool (Tools tab, gated on Kraken2), two new rules (`extract_domain_short`/`extract_domain_long`) running `extract_kraken_reads.py` on the ribodetector-clean reads. `mode` (prokaryote/eukaryote/both) isn't a real CLI flag, so it's serialized as a dict like MAGMA's `mags_annot`, not a flag string. Verified with a real `snakemake -n` dry-run (both `mode` values) and confirmed live in the running app (Tools tab card renders correctly, dropdown works, toggling Kraken2 gates it as expected) — see [[DOGMA]] for the full build log.
- **Literature review for DOGMA Phase 2 (2026-07-10)**: surveyed real metatranscriptomics methods papers (2020–2026, soil/sediment/water focus) to decide the assembly-onward design before writing any code. Landed on: multi-assembler ensemble (rnaSPAdes+MEGAHIT+Trinity) + MMseqs2 dedup instead of a single assembler; no co-assembly (stays per-sample, like MAGMA/SIGMA); CAZy/NCycDB added as optional extras alongside eggNOG-mapper (soil carbon/nitrogen-cycle relevance); an optional spike-in-concentration field reserved in the sample sheet schema now (absolute-quantification math deferred — needs a real wet-lab protocol first). Full citations and reasoning in [[DOGMA]]. None of this is built yet — decisions only.
- **User asked whether DOGMA's new multi-assembler-ensemble idea should extend to MAGMA/SIGMA too — researched, then declined for both.** For MAGMA the equivalent isn't contig-level dedup but bin-level consensus (bin each of several assemblies separately, feed all bins into the `binette` refinement MAGMA already has); for SIGMA (single-genome assembly) there's no contig-dedup equivalent at all — the established tool is Trycycler/Autocycler, long-read-only, its own heavier cluster+consensus workflow. **User's call: don't implement either** — both pipelines are stable/complete and not worth the added complexity right now. See [[Known Issues and Next Steps]].

## Database folder validation for manually-picked paths, and real fingerprint bugs found (2026-07-14/15)
- **Real gap, not a UI nit**: `DatabaseCard`'s folder-picker icon only did something useful if the database was already `configured` (re-points via `/databases/set` immediately, no check). For a not-yet-configured database, picking a path just set local UI state (`_destDir`) as a future download destination — there was no way to say "I already have this on disk, just use it" without going through an actual (re-)download. User explicitly wanted this fixed with a **check/validate button next to Download, inside each database's card** for exactly this manual-selection case.
- Implemented: `databases_engine.validate_database(pipeline_id, db_key, path)` (new) checks a single database's `detect_files`/`detect_dirs` fingerprint against the picked folder itself, or one immediate subdirectory (databases are sometimes nested one level deeper than what the user points at, e.g. VIBRANT below). ## Database downloads: survive navigation, real Cancelar, expand-when-configured (2026-07-16/17)
- **User report #1**: picking a folder + clicking "Validar" on any database card reloaded the *whole* Databases screen, interrupting other databases' in-progress downloads. Root cause: `DatabasesScreen._load()` (`app/lib/screens/databases/databases_screen.dart`) unconditionally set `_loading = true` on every call — including the refresh triggered by `DatabaseCard`'s `onChanged` callback after a successful validate — and `build()` returns *only* a spinner while `_loading`, dropping the entire `Wrap` of `DatabaseCard`s (all of them, not just the touched one). Each disposed card's `dispose()` called `_ws?.close()`, killing any other card's in-progress download WebSocket. Fixed: `_loading` spinner now only shows on the very first load (`_databasesRaw.isEmpty`); added `ValueKey(db.settingKey)` per card as a defensive guard against future reordering-caused remounts.
- **User report #2 (follow-up)**: downloads also stopped on navigating *away* from the Databases screen entirely (different sidebar tab) — not just a same-screen reload. Root cause: `AppShell` (`app_shell.dart`) shows `pages[index]` directly, no `IndexedStack`, so switching tabs fully unmounts `DatabasesScreen` (and every `DatabaseCard`, which owned the download's `WsClient` directly). Fixed with the same pattern already established for pipeline runs ([[Decisions Log]]'s autosave/disk-log entry, `pipeline_run_provider.dart`): moved download ownership into a new root-level Riverpod `Notifier`, `app/lib/services/database_download_provider.dart` (`databaseDownloadsProvider`), keyed by `"<pipelineId>:<dbKey>"`. `DatabaseCard` now reads/writes through it instead of owning a `WsClient`, and restores `_expanded`/`_destDir` from the provider's state in `initState` so a remount (tab switch) shows the in-progress card expanded again instead of blank. Backend mirrored this: download execution became a detached `asyncio.create_task` (`_download_task`/`download_tasks` in `backend/main.py`, keyed the same way) independent of any one websocket, with an **in-memory** (not disk-logged like pipeline runs — a big DB emits ~1 progress event per MB, disk replay would be huge) backlog (`download_log`/`download_progress`/`download_status`) for a reconnecting socket to catch up. Added a top-bar status indicator (`_DatabaseDownloadsIndicator`, mirrors `_RunningPipelineBanner`) showing downloading/error/done and tapping through to the Databases tab — needed lifting `AppShell`'s tab index out to a new `selectedTabProvider` (`providers.dart`) so a widget outside the nav rail could switch tabs.
- **Real race caught during this fix, not theoretical**: a naive "snapshot the backlog, replay it, *then* subscribe to live events" order in the websocket handler lost the download task's very first log line — `asyncio.create_task()` only *schedules* the coroutine, it doesn't run until the handler's own next `await`, so replaying "what's in the backlog so far" via `await websocket.send_json(...)` is exactly the await that lets the task start running and emit its first event, which then lands after the snapshot was already taken and before the queue subscription exists → dropped. Fixed by snapshotting the backlog and subscribing to the live queue in the same synchronous breath (no `await` between the two calls). **Caught and verified via a from-scratch integration test, not by inspection**: `starlette.testclient.TestClient.websocket_connect()` spins up a *fresh event loop per connection* (its own portal thread, torn down when the `with` block exits) — cannot be used to test a background task surviving a client disconnect, since the loop hosting it dies with the connection. Had to instead run the real app via `uvicorn.Server` in a background thread + the real `websockets` client library to get one persistent event loop across multiple connect/disconnect cycles, matching how production `uvicorn` actually behaves. Worth remembering this pitfall before reaching for `TestClient` on any future websocket-with-background-task test.
- **User report #3, found live-testing after report #2's fix shipped**: a Bakta database download "disappeared" after finishing, and re-selecting a smaller download option after having picked the large one first still downloaded the large one. Root cause: detaching the download from any one connection (the report #2 fix) meant the "Cancelar" button — which only ever closed the *client's own* websocket — stopped actually cancelling anything server-side (before the detach, the download ran inline inside the websocket handler, so closing the socket really did kill it via a `WebSocketDisconnect` propagating out of the handler). A "cancelled" download kept running in the background; the next "Baixar" click for the same database just silently reattached to that still-running stale task (whatever option/dest_dir it *originally* started with, ignoring the new selection) — confirmed as the live root cause of "the file disappeared" during manual reproduction, not guessed. Fixed: added a real `POST /api/pipelines/{pid}/databases/{db_key}/download/cancel` (`_cancel_download` helper, calls `task.cancel()`) that `DatabaseDownloadsNotifier.cancel()` now calls; every new websocket connection to `/ws/.../download` unconditionally cancels-and-restarts whatever was already running for that key with the new connection's params (safe because the frontend only ever opens this socket from an explicit Baixar click — never a passive reconnect, since the root-level provider already holds accumulated state across navigation without reopening a socket per report #2's fix). Verified with two more from-scratch `uvicorn`-in-a-thread integration tests: `/cancel` actually raises `CancelledError` inside the download coroutine and clears `download_tasks`; starting fresh with a different option after a stale run correctly uses the new params, including when the old one was never explicitly cancelled first. **Known, not-yet-fixed limitation**: cancelling (or an error) still doesn't clean up any partial file already written — same as a plain network failure already behaved before any of this, not a new regression, but worth revisiting if it recurs (see [[Known Issues and Next Steps]]).
- **Same session, explicit user ask**: `DatabaseCard`'s expand arrow did nothing once a database was already `configured`/"Validado" — the whole download-options block was gated by `_expanded && !db.configured`, so the chevron visibly flipped but revealed nothing. Uses the `choose_destination` l10n string that already existed but was unwired until now.
