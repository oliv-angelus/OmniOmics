# PRISM

Fifth OmniOmics pipeline: long-read amplicon/marker-gene sequencing. See [[Decisions Log]] for the naming story and [[Known Issues and Next Steps]] for the running status log; this note is the design/architecture reference, same role [[DOGMA]]/[[SIGMA]] play for their own pipelines. **The "Rule chain (first slice, built 2026-08-06)" section right below is the *original* 16S/ITS+GTDB-only design and is kept as historical record — for the real, current architecture (5 marker genes, GTDB+SILVA, real phylogenetic trees on both platforms, PICRUSt2 functional inference), see "Current architecture (as of 2026-08-07)" further down, right after the dated build log starts.**

## Name
**PRISM** = "Profiling rRNA Inference of Species via Metabarcoding" (P-R-I-S-M, verified letter-by-letter). Metaphor: a prism resolves mixed light into its component spectrum, same as the pipeline resolves a mixed environmental sample into its component taxa. Chosen over `ENIGMA`/`AMALGAMA` (rejected as forced) and a dropped `SIEVE` candidate whose own breakdown didn't actually spell "SIEVE" in order. `CENSUS` (Community/Ecological/Nucleotide/Sequencing/Universal-primers/Species) was the other finalist. Does not follow the MAGMA/SIGMA/DOGMA "-GMA" rhyme, same as DEFINE before it — the rhyme was never a hard requirement, real meaning is.

## Scope decisions (2026-08-06, both explicit user calls)
- **Long-read-only** — no short-read/DADA2-on-Illumina path at all, unlike MAGMA/SIGMA/DOGMA's short/long/hybrid branching.
- **Both platforms from the start**: ONT (Nanopore) *and* PacBio HiFi/CCS, not one first. This matters because they need genuinely different denoising algorithms (see Design below) — it was a real scope decision, not a detail.
- **Both marker genes from the start**: 16S (bacteria/archaea) *and* ITS (fungi), not 16S-first. 18S (protists/broader eukaryotes) deliberately deferred, not yet designed. (Superseded 2026-08-07 -- 18S, 23S, 28S all added, see the "More marker genes" section below.)

## Design, from real literature (full citations in [[Scientific References]])
- **PacBio HiFi and ONT cannot share one denoising algorithm.** HiFi/CCS reads are near-zero-error (Q93), so DADA2's own exact-sequence-inference model works directly (Callahan et al. 2019, 10.1093/nar/gkz569) — same core algorithm short-read Illumina uses, reparameterized. ONT reads, even current R10.4.1/Kit 14 (~99% per-read accuracy), are too error-prone for that model — Emu's expectation-maximization-against-a-reference approach is used instead (Curry et al. 2022, 10.1038/s41592-022-01520-4), not ASV-calling.
- **Chimera detection has a real, recently-documented false-positive problem on long reads.** Hakimzadeh et al. 2025 (10.7717/peerj.20456) found default chimera filters misclassify up to 55% of genuine reads as chimeric on real long-read amplicon data; `uchime_denovo`/`uchime3_denovo` was the most precise tested (9.8% FP at defaults) — that's why it's the tool used, with the caveat stated directly in the tool's own manifest description rather than silently trusted.
- **Taxonomy reference kept consistent with the rest of OmniOmics on purpose**: both platforms classify against the *same* GTDB-formatted 16S reference (Alishum's DADA2-formatted GTDB r220 SSU release, 10.5281/zenodo.13984843, built on Parks et al. 2022's GTDB, 10.1093/nar/gkab776) rather than the more common SILVA/Greengenes default — because the Plots tab's `build_phyloseq.R` (MAGMA/SIGMA/DOGMA) already expects GTDB-style 7-rank `d__;p__;c__;o__;f__;g__;s__` lineage strings, so PRISM's 16S output can become a Plots-tab input later with no new R code. ITS uses UNITE instead (Nilsson et al. 2019, 10.1093/nar/gky1022) since GTDB is bacteria/archaea-only, doesn't cover fungi.
- **Long-read platform is a run-wide choice, not per-sample** — reuses the exact `long_read_platform` mechanism DOGMA's manifest already established for Flye/SPAdes flags (`config_engine.py`), just consumed differently (picks which denoising engine's rule actually executes, via the same if/else-touch idiom `fastp`/`filtlong` already use for their own read-type branching — the other engine's rule touches empty outputs rather than being skipped at the DAG level).
- **Marker gene (`--gene`, 16S/ITS) is a wrapper-script-level flag, not a manifest dict-param** — `dada2_pacbio`/`emu_ont`'s own flag string carries it (parsed by the R/Python scripts themselves via optparse/argparse), unlike DOGMA's `domain_filter.mode` which needed the dict-shaped-param mechanism. No `config_engine.py` changes needed either way.

## Rule chain (first slice, built 2026-08-06)
```
raw long reads (ONT or PacBio HiFi, per-run choice)
  -> NanoPlot (raw QC)
  -> Filtlong (length/quality filter, 16S/ITS-appropriate window)
  -> NanoPlot (clean QC)
  -> Cutadapt (primer trim + orient, linked adapter, discard-untrimmed)
  -> VSEARCH dereplicate -> uchime3_denovo -> recover_nonchimeric_reads.py
       (maps the chimera verdict on dereplicated centroids back onto every
        original read via VSEARCH's own --uc cluster mapping)
  -> [platform branch]
       PacBio HiFi -> dada2_pacbio.R (cohort-level: learnErrors -> dada() ->
                      makeSequenceTable -> assignTaxonomy against GTDB/UNITE,
                      collapsed to one row per unique lineage)
       ONT        -> emu_build_db (once per --gene, GTDB/UNITE -> Emu's
                      sequences+taxonomy-list format) -> emu_classify
                      (per sample) -> join_emu_tables.py (cohort-level join)
  -> select_abundance_table (whichever engine ran -> one stable output path)
  -> results/05_ABUNDANCE_TABLE/prism_abundance_table.tsv
     (tax;lineage rows x sample columns -- same shape MAGMA's own abundance
      table already uses)
```
Manifest categories: QC & Trimming, Primer Removal, Chimera Filtering, Denoising & Classification. Sample sheet is long-reads-only (`long_reads_dir`, no `short_reads_dir` at all) — `build_samples()` needed zero changes, every discovered sample is automatically `read_type: "long"`, same "generic enough to reuse unmodified" story [[Decisions Log]] already tells for SIGMA reusing MAGMA's sample discovery.

One new small Dart change (not zero, unlike adding tools to an *existing* pipeline): `PipelineCategory.metabarcoding` added to `app/lib/theme/category_colors.dart` (lime accent `#65A30D`, not yet used by another category) since no existing placeholder category fit — the original six placeholders (Transcriptômica → now DEFINE, Metatranscriptômica → now DOGMA, Proteômica, Metaproteômica, Metabolômica, Single-cell) plus Pangenômica/Genotipagem never included an amplicon/metabarcoding slot.

## Current architecture (as of 2026-08-07) — supersedes the diagram above
Everything below is real-tool/real-Snakemake-verified (see the dated log sections further down for exactly how); this is just the current shape in one place instead of scattered across a dozen dated entries.
```
raw long reads (ONT or PacBio HiFi, per-run choice: long_read_platform)
  -> NanoPlot (raw QC) -> Filtlong (length/quality filter)
  -> NanoPlot (clean QC) -> Cutadapt (primer trim + orient, gene-appropriate primers)
  -> VSEARCH cluster (95% identity, NOT exact dereplication -- raw noisy long
       reads never exact-duplicate) -> uchime_denovo (classic, not uchime3)
       -> recover_nonchimeric_reads.py (chimera verdict on clusters -> every
          original member read, via VSEARCH's own --uc cluster mapping)
  -> [platform branch]
       PacBio HiFi -> dada2_pacbio.R (cohort-level: learnErrors -> dada() ->
                      makeSequenceTable -> assignTaxonomy against the
                      resolved --gene/--reference_db reference) ->
                      real ASV-level output (prism_asv_sequences.fasta,
                      prism_asv_taxonomy.tsv, prism_asv_counts.tsv) ->
                      DECIPHER align -> phangorn NJ -> GTR+G+I ML tree
                      (prism_tree.nwk, skipped if <3 ASVs) -> lineage-collapse
                      for the primary abundance table (unchanged shape)
       ONT        -> emu_build_db (once per --gene, resolved reference ->
                      Emu's sequences+seq2tax+taxonomy-list format) ->
                      emu_classify (per sample, --keep-counts for real read
                      counts not fractions) -> join_emu_tables.py
                      (cohort-level join; also emits a tax_id-level
                      prism_species_counts.tsv alongside the primary
                      lineage-collapsed table) -> emu_tree (closed-reference:
                      extracts the ACTUAL detected reference sequences from
                      Emu's own db, same DECIPHER/phangorn method via the
                      shared lib/build_tree.R -> prism_tree.nwk +
                      prism_species_taxonomy.tsv, skipped if <3 species)
  -> select_abundance_table (whichever engine ran -> one stable output path)
  -> results/05_ABUNDANCE_TABLE/prism_abundance_table.tsv
     (tax;lineage rows x sample columns -- same shape MAGMA's own abundance
      table already uses)
  -> [optional, PacBio+16S only] picrust2: phylogenetic placement + hidden-
       state prediction -> KO/EC/pathway abundance tables (functional
       inference from 16S taxonomy alone, no shotgun data -- Douglas et al.
       2020). Real execution deliberately not run yet (RAM constraint, see
       the "PICRUSt2" dated section) -- DAG-wired and dry-run-verified only.
```
**Marker genes**: 16S, 18S, 23S, 28S, ITS (`--gene`). **Reference databases** (`--reference_db`): GTDB (16S bacteria/archaea only, DADA2-pre-formatted) or SILVA (SSU serves 16S+18S, LSU serves 23S+28S, raw release needing a real header/RNA→DNA conversion pass, `convert_silva_headers.py`) or UNITE (ITS fungi only, always used regardless of `--reference_db`). Resolution logic lives in one place, `04_denoise_classify.smk`'s `_resolve_ref_path()`.

**Phylogenetic trees**: both platforms now produce a real `prism_tree.nwk` (PacBio: from real ASV sequences; ONT: closed-reference, from Emu's own matched reference sequences), wired into the Plots tab's `phyloseq` object (`build_phyloseq()` auto-detects and switches to ASV/species resolution + a real `phy_tree()` when one exists) -- this is what unlocks real `unifrac`/`wunifrac` distances in `beta_diversity.R`. No tree (MAGMA/DOGMA, or a PRISM run with <3 detected taxa) -- `build_phyloseq()` falls back to the original lineage-collapsed shape unchanged.

**Functional inference**: PICRUSt2 (16S taxonomy -> predicted KO/EC/pathway abundances, no shotgun sequencing needed), PacBio+16S only (its reference tree is bacteria/archaea-16S-specific, and only that path has real per-ASV sequences to place). Implemented and DAG-verified; real execution intentionally not run on this dev machine (see below).

**Still not implemented**: GROND / full 16S-ITS-23S rrn-operon mode (needs its own primer-set design decision); real full-size SILVA file download/validation (only a small fragment tested so far).

## Real tool install + real-data smoke test (2026-08-06, same day, follow-up pass)
User explicitly asked to install Emu and DADA2 and test for real, not just dry-run. Built 5 real conda envs (`prism-emu`, `prism-dada2`, `prism-cutadapt`, `prism-vsearch`, on this dev machine) and tested against **real** data: 3 real full-length 16S sequences fetched live from NCBI (E. coli `NR_024570.1`, B. subtilis `NR_113265.1`, P. aeruginosa `NR_117678.1`, not fabricated), with synthetic PacBio-HiFi-like (mean Q33, ~0.05% per-base error) and Nanopore-like (mean Q20, ~1% per-base error + indels) reads simulated from them with a real Phred-derived error model (quality score *is* `-10log10(p_error)`, matching real sequencer calibration), including one deliberately constructed chimeric read (E. coli 5' half + B. subtilis 3' half).

**Real bugs found and fixed, each confirmed by reproducing the failure then confirming the fix, not guessed:**
1. **Emu 3.5.1 (pinned version) has a real bug in `emu abundance` for any custom `--taxonomy-list` database**: crashed with `ValueError: f sums to 0, rather than 1`. Root cause traced by reading the installed source directly: `taxonomy.tsv`'s `tax_id` column is read with `dtype=str` while each alignment's tax_id is parsed as `int(ref_name.split(":")[0])`, so every frequency-dict lookup silently fails (`"1" != 1` as dict keys) — not specific to PRISM's database, would hit any custom Emu database built this way. Fixed upstream in Emu 3.6.0 (`dtype={'tax_id': 'int64'}`, confirmed by reading the 3.6.2 source) — `envs/emu.yaml` repinned to `emu>=3.6.2`.
2. **`emu build-database`'s real CLI needs `--seq2tax`**, a third file this script didn't generate at all (only `--sequences`/`--taxonomy-list`) — confirmed against a real `emu build-database --help`, not assumed. `build_emu_taxonomy.py` now also emits a `seq2tax.tsv` (trivial 1:1 tax_id-to-itself mapping, since every reference sequence gets its own unique tax_id). Also fixed a real path collision: the script's own intermediate sequences FASTA was named `species_taxid.fasta`, the exact filename `emu build-database` itself writes into the same output directory — renamed to avoid the two clobbering each other.
3. **`build_emu_taxonomy.py`'s reference-header parsing was wrong**: assumed `>Accession Domain;Phylum;...` (an ID token before the lineage). A live fragment of Alishum's real GTDB r220 SSU release (fetched from Zenodo, not assumed) confirmed the real format has **no accession at all** — pure `>Domain;Phylum;...;Species` from the very first character after `>`. Fixed the header parsing (no more `.split(None, 1)`). This also matches DADA2's own real `assignTaxonomy()` contract (confirmed via `?assignTaxonomy`'s help text) — the first version of the synthetic test reference fasta used the wrong (accession-prefixed) format too and silently produced a garbage merged taxon; fixed there also.
4. **`bioconductor-dada2=1.34.0` fails to load at all** on a freshly solved env: `undefined symbol: _ZTIN3tbb4taskE`. Root cause: dada2's compiled `.so` references the classic pre-2021 TBB API (`tbb::task`), but the conda solver's default (unpinned) `r-rcppparallel` resolves to a current build (5.1.11_2) that dropped TBB's old bundled-static-library approach in favor of dynamically linking `tbb>=2023.0.0` (oneTBB, which removed `tbb::task` entirely) — a real ABI-drift gap between when dada2's binary was built and what RcppParallel currently ships. Fixed by pinning `r-rcppparallel=5.1.9` (a build with no external tbb dependency, matching dada2 1.34.0's own build era) in `envs/dada2.yaml` — confirmed via a real `library(dada2)` load test before and after.
5. **`join_emu_tables.py` joined Emu's own `unmapped`/`mapped_filtered`/`mapped_unclassified` bookkeeping rows as a bogus empty-lineage taxon** (`d__;p__;c__;o__;f__;g__;s__`) — found by inspecting real Emu output, not assumed. Fixed by skipping rows whose `tax_id` is one of those three known summary labels.

**Verified correct after fixes, against real ground truth, not just "it ran":**
- **Emu 3.6.2**, real custom GTDB-shaped database, real ONT-like reads (116 reads, 3 species + 1 chimera): recovered relative abundances 0.526/0.302/0.172 for E. coli/B. subtilis/P. aeruginosa — matches the planted 60/35/20 read-count ratio (0.522/0.304/0.174) almost exactly.
- **DADA2 (`dada2_pacbio.R`)**, real PacBio-HiFi-like reads (240 reads, 3 species): recovered **exact** counts — 120 E. coli, 75 B. subtilis, 45 P. aeruginosa, matching the planted counts exactly, correct GTDB-style lineage strings, correct taxonomy at every rank.
- Both required a **real methodology fix along the way**, documented for future reference: an early version of the synthetic-read generator assigned quality scores in a hard-coded bimodal way (fixed low value at injected-error positions, fixed high value elsewhere) — this is *not* how real sequencers calibrate quality, and it broke DADA2's `learnErrors()`/`dada()` badly enough that 3 clearly-divergent real species collapsed into one bogus merged ASV even at a very low ~0.3% injected error rate. Confirmed via a controlled side-by-side test (same 2 species, zero injected errors + realistic quality noise only → correctly separated; same 2 species + the old bimodal quality/error scheme → collapsed to one). Fixed by generating quality scores first (`Normal(mean_q, 3)`) and deriving each base's error probability *from* that quality (`p = 10^(-Q/10)`), matching real Phred semantics — not a pipeline bug, but a real trap worth remembering for any future synthetic long-read fixture in this app.
- `cutadapt` (real 4.9, not simulated): 108/116 ONT-like reads correctly primer-trimmed and oriented (93% — realistic given ~1% per-base error can corrupt a 20bp primer site enough to miss detection at `-e 0.1`).

**Chimera-detection design gap — found, then fixed and verified the same day (2026-08-07).** Original finding: running `vsearch --uchime3_denovo` on raw (pre-denoising) reads, even after exact dereplication *and* after clustering at 99% identity, found **0 chimeras** in the test data — including the one deliberately constructed chimeric read. Root cause: raw noisy long reads (even at a realistic ~1% ONT error rate) essentially never exact-duplicate or even 99%-cluster with each other (every read differs from every other read of the *same* species by roughly 2× the per-base error rate, ~2%, already below a 99% clustering threshold) — so every dereplicated/clustered "cluster" ends up abundance=1, and `uchime3_denovo`'s parent/child abundance-skew logic has no signal to work with on singletons.

**Fix (kept the same pipeline position, changed the method — no full reorder needed after all)**: rather than moving chimera-checking to after denoising, testing found a smaller, surgical, empirically-validated fix works at the *same* pre-denoising position: (1) cluster raw reads at **95% identity** (`vsearch --cluster_size --id 0.95`, not exact dereplication) before chimera-checking — confirmed empirically that real same-species long reads stay comfortably above 95% pairwise identity at realistic ONT/PacBio error rates (giving real abundance-weighted clusters, e.g. 56/13/18-member clusters in the real test instead of all-singletons) while real between-species 16S divergence (tested against 3 genuinely different real organisms) stays nowhere near close enough to cross-contaminate a cluster — checked cluster membership directly, zero cross-species mixing at any tested identity down to 92%. (2) Switched from `--uchime3_denovo` to classic `--uchime_denovo` — re-tested both against the same real 95%-clustered data: `uchime3_denovo` *still* found 0 chimeras even with real abundance now available, while classic `uchime_denovo` at default settings correctly and precisely flagged **exactly** the one planted chimera, zero false positives. This actually matches Hakimzadeh et al. 2025 more faithfully than the original implementation did — that paper found `uchime_denovo` (not `uchime3_denovo`) was the most precise algorithm tested, and the very first version of this manifest's tool description already said "uchime_denovo" even though the code underneath had drifted to `uchime3_denovo`.

New rule `vsearch_cluster` replaces `vsearch_dereplicate`; `vsearch_chimera` now runs classic `uchime_denovo`. New manifest flag `--id` (default 0.95, clustering identity threshold, user-adjustable per platform). `recover_nonchimeric_reads.py` needed **no code changes** — the `.uc` cluster-mapping format is identical regardless of which vsearch clustering mode produced it.

**Verified end-to-end with the exact final rule commands** (not just ad hoc testing): real ONT-like test data (108 primer-trimmed reads, 3 species + 1 planted chimera) → 17 clusters formed (12 singletons, up to 56-member clusters) → `uchime_denovo` flags exactly 1 chimera (the planted one, zero false positives) → `recover_nonchimeric_reads.py` correctly keeps 107/108 original reads, all 3 species intact (31 B. subtilis / 57 E. coli / 19 P. aeruginosa) → fed through the real Emu classify step → final abundances 0.533/0.290/0.178, an even tighter match to the true 60/35/20 read-count ratio (0.522/0.304/0.174) than before the chimeric read was contaminating the signal.

## Plots tab wiring started (2026-08-07, same day) -- task list item #5
User asked to start this once the pipeline itself was real-verified. One real, load-bearing bug found and fixed *before* the wiring itself, plus the actual wiring, both real-tested against real (not fabricated) PRISM output.

- **Real bug found while starting this**: Emu's ONT-path table was relative abundance (0–1 floats), while MAGMA's own abundance table (and PRISM's own PacBio/DADA2-path table) is real read counts -- a real inconsistency that would have silently broken any count-based Plots-tab method (`differential_abundance_deseq2.R` needs real counts, not fractions, to be statistically valid; DESeq2's internal size-factor estimation assumes integers). Fixed at the source: `emu_classify` now passes `--keep-counts` (confirmed via a real `emu abundance --help` and a real run this adds an "estimated counts" column matching planted read counts almost exactly, e.g. 56.999999... for a true 57), and `join_emu_tables.py` now reads that column (rounded to nearest integer) instead of "abundance" -- so both platforms' final tables are now real counts, consistent with MAGMA's own convention.
- **File-discovery generalized**: `load_phyloseq.R` hardcoded MAGMA's exact filename (`abundance_table_final_RAW.tsv`) -- PRISM's real final output is named `prism_abundance_table.tsv` (see `select_abundance_table` in `04_denoise_classify.smk`), a genuinely different name. 1. **Unweighted UniFrac + `ape::pcoa()` crash on an all-zero distance matrix**: the first real `--distance_method unifrac` run against the 6-sample/5-species ONT tree object crashed inside `ordinate()` with a raw, Portuguese-locale `"row names contain missing values"` error. Root cause, confirmed by reproducing it directly against a hand-built all-zero `dist` object: unweighted UniFrac only considers presence/absence per tree branch, not abundance -- and in this dataset every sample genuinely contains all 5 species (just at different relative abundances), so every pairwise unweighted-UniFrac distance is mathematically, correctly 0. `ape::pcoa()` has no real handling for a totally degenerate (all-zero) distance matrix. Fixed with a clear guard (same philosophy as the pre-existing PCoA rank-deficiency guard, the other axis of "not enough real variation to ordinate") that explains *why* and suggests `wunifrac`/`bray`/`jaccard` instead. **`wunifrac` (weighted UniFrac) itself worked correctly and gave a real, ecologically sensible result** on the same data (axis 1 explaining 98.5% of variance, cleanly separating the coastal vs. inland groups) -- confirming the tree wiring itself is sound; the crash was specifically an unweighted-UniFrac-on-this-particular-data edge case, not a wiring bug.
2. **A real, pre-existing (not introduced this pass) file-resolution bug**, caught while testing the no-tree fallback path: `ABUNDANCE_FILE_PATTERNS["prism"]`'s simple filename pattern matches THREE files in a real PRISM run (`results/04_DENOISE/dada2/prism_abundance_table.tsv`, `results/04_DENOISE/emu/prism_abundance_table.tsv`, and the real merged `results/05_ABUNDANCE_TABLE/prism_abundance_table.tsv`) -- `find_input_file()`'s `hits[[1]]` picked whichever sorted first alphabetically (`04_DENOISE/...`), which for an ONT-platform run is the DADA2 branch's *empty* touch-placeholder, not the real Emu output. This had been silently masked in every earlier real test because the PacBio runs used so far happened to have DADA2 (the alphabetically-first branch) as their real active platform. First attempted fix (anchoring the regex pattern to include the `05_ABUNDANCE_TABLE/` path prefix) turned out not to work at all -- confirmed directly that R's `list.files(pattern=)` only ever matches a file's **basename**, never its directory path, contrary to what the pattern's apparent path-like shape suggests. Real fix: `find_input_file()` gained an optional `prefer` substring parameter -- when a pattern matches more than one file, the first hit whose *full path* contains `prefer` wins over plain (alphabetical) list order; `ABUNDANCE_FILE_PATTERNS["prism"]` now sets `prefer = "/05_ABUNDANCE_TABLE/"`. MAGMA's own pattern is unaffected (its filename really is unique in the tree, confirmed by grepping its own `.smk` rules).

**Verified for real, end-to-end, both platforms, both with and without a tree:**
- PacBio (1 sample, 3 ASVs): `load_phyloseq.R` correctly builds a 3-taxa ASV-resolution object with a real 3-tip tree attached, `has_tree=true`.
- ONT/Emu (6 samples, 5 species): `load_phyloseq.R` correctly builds a 5-taxa species-resolution object with the real 5-tip tree attached; `beta_diversity.R --distance_method wunifrac` produced a real, sensible ordination (see bug #1 above); `bray` unaffected/unchanged; `unifrac` gives the clear degenerate-data error from bug #1.
- The same ONT run's tree file temporarily moved aside and re-loaded: correctly falls back to the original 5-taxa lineage-collapsed shape, `has_tree=false`, and `unifrac`/`wunifrac` now correctly give the new clear pre-flight error instead of any crash.
- A single-sample ONT run (no tree ever built, <3 species): correctly resolves to the real merged `05_ABUNDANCE_TABLE` file (bug #2's fix), `has_tree=false`.
- Regression-checked two already-verified analyses (`alpha_diversity.R`, `taxonomic_composition.R`) against the new ASV/species-resolution object -- both still complete successfully, confirming the resolution change (collapsed lineage -> real ASV/tax_id rows, for tree-carrying runs specifically) doesn't break analyses that don't care about the tree at all.

**Task #9 is now done.** Zero Flutter changes needed (confirmed: `metadata_columns.json`'s consumer, `plot_loaded_data.dart`, reads specific named fields, so the new `has_tree` key is simply ignored -- same "manifest/JSON-driven, no frontend gating" pattern already established for `tax_ranks`).


## GROND / operon rrn completo + presets de amplicon (2026-08-09)
Pedido do usuário: implementar o GROND. Durante o desenho, ele levantou que o PRISM
serve a vários tipos de amplicon e perguntou como o usuário selecionaria isso — o que
expôs um **bug real de usabilidade já existente**: "16S" estava codificado em TRÊS
lugares independentes (primers do cutadapt, janela do filtlong, `--gene` das engines).
Trocar só o `--gene` (o único que parece "a escolha do marcador") deixava primers e
janela de 16S no lugar: o cutadapt roda com `--discard-untrimmed` e descartaria quase
tudo, e o filtlong o resto — **sem erro nenhum**, só resultado vazio. Para o operon
(~4,3 kb vs. a janela de 1300-1700) seria garantido.

**Solução (escolha do usuário): bloco `amplicon_presets`**, mesma forma/mecanismo do
`long_read_platforms` que já existia (declarado no manifest, resolvido uma vez no
`config_engine.py`, lido pelas regras via `config["amplicon_preset"]`, dropdown na aba
Entradas). Uma escolha carrega marcador + banco + primers + janela juntos. 9 presets.
A pedido do usuário ("existem diferentes primers que amplificam a mesma região"), os
primers continuam **editáveis**: um `-g/-G` digitado na aba Ferramentas vence o preset
(mesmo para `--min_length/--max_length`), e há um preset "custom" que não preenche nada.

**Sequências reais, obtidas de fonte primária, não de memória:**
- Operon rrn: 16S-27F + 23S-2241R (`ACCRCCCCAGTHRAACT`), ~4,3 kb, Cuscó et al. 2019.
  A sequência do 2241R que eu tinha de memória estava **errada** — pesquisar evitou um
  primer silenciosamente incorreto.
- Kit ONT do laboratório do usuário (SQK-MAB114.24): sequências extraídas do PDF oficial
  da ONT (lido e apagado a pedido). Achado real: **o kit é um MIX**, não um par único —
  agrupa o par universal com pares taxon-específicos (Borrelia/Chlamydia no 16S;
  Fusarium/Malassezia/Pythium no ITS). O preset passa todos os pares ao cutadapt, que
  aceita `-g` repetido, refletindo como a PCR de fato se comporta. Todas em
  [[Scientific References]].
- 18S/23S/28S: **não consegui confirmar primers em fonte real**, então os presets desses
  vão com primers VAZIOS e rótulo "informe os primers" em vez de sequências inventadas.

**Banco GROND** (`gtdb207nr_nrRep.fna.gz` + `gtdb207nr_taxRep.tsv`, Zenodo
10.5281/zenodo.10889037), adicionado à aba Bancos de dados. Formato real confirmado
baixando fragmentos: headers são IDs opacos de cluster SEM taxonomia, que vive num TSV
separado sem cabeçalho e com ranks separados por PIPE — então precisou de um JOIN real
entre dois arquivos (`convert_grond_headers.py`), não uma reescrita de header como o
SILVA. Usa o campo `extra_files` do downloader para o segundo arquivo.

**Três bugs pré-existentes encontrados no caminho** (todos invisíveis porque nenhum
download real de banco jamais foi executado — é o item de validação ainda em aberto):
o downloader **auto-descomprime** `.gz`, mas (1) o `post_cmd` do SILVA SSU e (2) o do
SILVA LSU referenciavam o nome `.fasta.gz`, e (3) o `detect_files` do GTDB esperava
`*.fa.gz` — ou seja, os três quebrariam no primeiro download real. Corrigidos.

**Verificado de verdade**: conversor rodado contra fragmento real do GROND (174 seqs,
headers idênticos ao formato GTDB que o PRISM já consome); `post_cmd` do manifest
executado ponta a ponta deixando exatamente o arquivo que o `detect_files` espera;
lógica das regras testada nos 3 presets + override manual + preset vazio; e um
`snakemake -n` real com o preset do operon gerando os comandos corretos
(`filtlong --min_length 3500 --max_length 5000`,
`cutadapt -g AGRGTTYGATYMTGGCTCAG...AGTTYDACTGGGGYGGT`, `--ref .../grond_rrn_dada2.fasta`).
O preset 16S padrão produz exatamente os mesmos primers do default antigo — sem regressão.

**Correção de UX encontrada pelo usuário (2026-08-09)**: o dropdown oferecia presets
como "18S — informe os primers" e "Personalizado — informe tudo", mas **não havia campo
nenhum para informar os primers**. O único caminho era digitar `-g/-G` cru no campo de
parâmetros do cutadapt na aba Ferramentas — nada descobrível, e exigia conhecer a sintaxe
de flags do cutadapt. Um preset dizer "informe os primers" sem oferecer onde informar é um
beco sem saída real, não um detalhe.

Corrigido com dois campos de texto reais na aba Entradas, logo abaixo do dropdown:
pré-preenchidos pelo preset escolhido (então o usuário VÊ quais sequências serão usadas,
em vez de precisar confiar), editáveis, e aceitando **vários primers separados por
vírgula** — necessário porque o kit ONT é um mix real, não um par único. Trocar de preset
repreenche os campos; o que o usuário digitou vence e sobrevive ao rascunho salvo. Campo
vazio cai de volta no preset em vez de apagar as sequências dele (senão só abrir a aba e
salvar zeraria os primers silenciosamente). Nenhuma regra do Snakemake mudou — o
`config_engine.py` apenas substitui os primers dentro do bloco `amplicon_preset` que as
regras já liam. Verificado ponta a ponta: preset 18S (sem primers) + sequências digitadas
→ `cutadapt -g AACCTGGTTGATCCTGCCAGT...GTAGGTGAACCTGCAGAAGGATCA -e 0.1`. `flutter analyze`
limpo e `flutter build linux` OK.

SILVA); nenhum teste com dados reais de operon; 12S (eDNA de vertebrados) fica anotado

## Ícone (2026-08-09) — código de barras, não prisma
Gerados 6 conceitos no estilo dos outros 4 pipelines (fundo quadrado-arredondado escuro,
um glifo em traço grosso, gradiente na cor da categoria — lime `#65A30D`), e montada uma
folha de comparação mostrando cada um em tamanho grande, nos tamanhos reais de uso
(96/64/40 px) e ao lado da família existente.

**A folha comparativa mudou a recomendação, e vale registrar por quê**: eu havia sugerido
o conceito do prisma com refração (o mais literal ao nome). Ver renderizado a 40px mostrou
que os feixes viram um borrão, e a linha "ao lado da família" mostrou que ele era
visivelmente mais detalhado que os quatro irmãos, que usam formas únicas e grossas.
Também só ficou evidente lado a lado que um triângulo puro competiria com o losango do
DEFINE. Lição prática: julgar ícone em tamanho grande engana; a comparação em tamanho de
uso e em contexto é que decide.

**Escolha do usuário: código de barras** — "metabarcoding" é literalmente o que o pipeline
faz. Correção real aplicada sobre a primeira versão: barras de alturas variadas leem como
*gráfico de barras* (conflitando com a aba Gráficos); códigos de barras reais têm altura
**uniforme** e **larguras** variadas. A versão instalada (D3) tem 5 barras grossas de
altura uniforme e larguras variadas — a única variante que continua legível a 40px.
Trade-off aceito conscientemente: o ícone comunica "metabarcoding", não o prisma do nome.
